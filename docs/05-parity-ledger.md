# 05 — Parity Ledger

A living, queryable record of parity state. It answers "what percentage of
the Swiftfin set works" and "what is unimplemented" without anyone reading
code. The ledger is generated, not hand-maintained.

## Files

```
ledger/
  deadfin-routes.json  generated snapshot — Deadfin route table export
  shadow-spec.yaml     hand-curated — hidden routes: path, upstream file:line, client set
  annotations.yaml     hand-edited — deferred/stub reasons, Swiftfin membership, WebSocket states
  parity.json          generated — one row per HTTP operation (364 spec + shadow)
  websocket.json       generated — one row per SessionMessageType (34)
  PARITY.md            generated — human-readable roll-up
```

## Route snapshot boundary

The route snapshot is generated externally and committed. `make ledger-routes`
refreshes it from a clean Deadfin checkout:

```
make ledger-routes DEADFIN_DIR=<deadfin-master-checkout> DEADFIN_REF=<40-character-revision>
```

The target rejects a dirty checkout or a HEAD that does not match
`DEADFIN_REF`. It runs `go run ./cmd/deadfin routes --json` from that checkout.
It does not consume a prebuilt Deadfin binary.

`make ledger` reads the committed snapshot. It does not require a Deadfin
checkout. This split obeys the clean-checkout CI boundary: the CI workflow
excludes the ignored Deadfin checkout.

## Row shape (`parity.json`)

```json
{
  "id": "GetPostedPlaybackInfo",
  "method": "POST",
  "path": "/Items/{itemId}/PlaybackInfo",
  "subsystem": "MediaInfo",
  "status": "done",
  "registered": true,
  "shadow": false,
  "clients": ["swiftfin", "web"],
  "reason": ""
}
```

The `status` field uses these values:

| Status | Meaning |
|---|---|
| `done` | Route registered and all corpus steps pass |
| `partial` | Route registered but no evidence, or some steps fail |
| `stubbed` | Registered intentional stub (LiveTv, SyncPlay) |
| `deferred` | Deferred by annotation; route intentionally not served |
| `todo` | Route not registered and not deferred |

The `disposition` field is `deferred` for the stubbed LiveTv and SyncPlay
cohort (decision D2). It is separate from `status`.

## Status derivation

The generator derives each HTTP status in this order:

1. A deferred annotation with no route produces `deferred`.
2. A registered intentional stub produces `stubbed`.
3. A missing unannotated route produces `todo`.
4. A registered route without corpus evidence produces `partial`.
5. A registered route with any failed step produces `partial`.
6. A registered route with evidence produces `done` only when every step passes.

## Swiftfin REST set

The Swiftfin REST denominator is 95 operations. The generator fails unless
the REST set contains exactly 95 distinct operations. SDK conveniences that
never appear as `Paths.*` (authentication, `/socket`, UDP discovery) are in a
separate generated section, not in the REST fraction.

## Ratchets

An optional `ratchet` flag in annotations marks a done row as a floor. A
ratcheted done row fails generation if current evidence no longer supports
done. An upstream pin reset can clear a ratchet only with an explicit
`x-jellyfin-pin` change. The generator records that reset in the source
metadata.

## Generation contract

1. `make ledger-routes` refreshes the external route snapshot.
2. `make ledger` rewrites `parity.json`, `websocket.json`, and `PARITY.md`
   from committed inputs.
3. `make ledger-check` compares generated bytes with committed files. It
   exits nonzero if any file is stale.
4. `make verify-ledger` runs focused ledger tests and `ledger-check`.

The only writable inputs are `annotations.yaml` and `shadow-spec.yaml`. The
route snapshot is writable only through `make ledger-routes`. Generated files
are overwritten by `make ledger`.
